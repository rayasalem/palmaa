# تقرير تحليل بيئة الإنتاج — Palma Marketplace

**البيئة:** Production (لا تعديل مباشر على المستخدمين أو البيانات الحية)  
**النطاق:** تقييم فقط — لا تجارب ولا تعديلات على الكود أو البيانات.

---

## 1. تحليل الأمان

| #    | البند                                  | التقييم | الملاحظات                                                                                                                                                                |
| ---- | -------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 1.1  | **JWT / إصدار والتحقق**                | جيد     | إصدار وتحقق من جانب الخادم؛ إلزام `JWT_SECRET` (≥32 حرف) في الإنتاج؛ انتهاء الصلاحية (مثلاً 7d).                                                                         |
| 1.2  | **Cookies**                            | جيد     | httpOnly، secure في الإنتاج، sameSite: none للـ cross-origin؛ اسم ثابت (مثلاً palma_token).                                                                              |
| 1.3  | **تخزين التوكن في الواجهة**            | جيد     | لا يُخزَّن JWT في localStorage؛ يُستخدم sessionStorage فقط عند cross-origin للـ Bearer؛ القراءة للتوكن تدعم القراءة من localStorage للتوافق القديم فقط.                  |
| 1.4  | **إدارة الجلسات (token_version)**      | جيد     | حقل `token_version` في `users` (migration 011)؛ التحقق من `ver` في JWT مقابل DB؛ `POST /api/auth/logout-all` يزيد الإصدار ويلغي كل الجلسات. _يتطلب تشغيل migration 011._ |
| 1.5  | **MFA (TOTP)**                         | جيد     | حقول `mfa_enabled` و `mfa_secret`؛ مسارات setup، verify-setup، verify، status، disable؛ اختياري وتدريجي. _يتطلب migration 011._                                          |
| 1.6  | **صلاحيات المستخدمين (RBAC)**          | جيد     | `authenticate`، `optionalAuth`، `requireRole(ADMIN                                                                                                                       | MERCHANT                                                                            | …)` مطبقة بوضوح؛ حماية مسارات الإدارة والطلبات والسلة والمنتجات (تعديل/حذف). |
| 1.7  | **التحكم في الوصول للطلبات**           | جيد     | `GET /api/orders/:id`: مالك (عميل/تاجر) أو ADMIN أو `X-Order-Guest-Token` صالح؛ لا يُعاد `guest_access_token` في الاستجابة.                                              |
| 1.8  | **Rate limiting عام**                  | جيد     | حد عام (مثلاً 200/15 دقيقة) عبر `generalLimiter`؛ قابل للتكوين بـ `RATE_LIMIT_MAX`.                                                                                      |
| 1.9  | **Rate limiting لكل endpoint**         | جيد     | Auth: authLimiter؛ دفع: paymentLimiter؛ تعليقات: commentLimiter؛ منتجات: productListLimiter (100/15 دقيقة)، productByIdLimiter (300/15 دقيقة) مع env.                    |
| 1.10 | **تسجيل 429**                          | جيد     | عند تجاوز الحد: تسجيل مع requestId و IP مقنّع؛ عداد في `/metrics` (rate_limit_hits).                                                                                     |
| 1.11 | **التحقق من المدخلات (Validation)**    | جيد     | طبقة Joi مركزية؛ `validate(schema, 'body'                                                                                                                                | 'query', source)` على auth، cart، orders، products، MFA؛ رفض 400 وتسجيل validation. |
| 1.12 | **تخزين بيانات حساسة في localStorage** | جيد     | لا يُخزَّن JWT في localStorage. المُخزَّن: `palma_current_user` (عرض)، `palma_cart` (سلة ضيف)، لغة، تفاصيل شحن مؤقتة (orderId). لا كلمات سر ولا توكنات.                  |
| 1.13 | **مفاتيح الخدمة (Supabase)**           | جيد     | `SUPABASE_SERVICE_KEY` في الخادم فقط (env)؛ الواجهة تستخدم `VITE_SUPABASE_URL` و `VITE_SUPABASE_ANON_KEY` فقط.                                                           |
| 1.14 | **مفاتيح الدفع**                       | جيد     | مسارات الدفع محمية؛ استخدام paymentLimiter؛ لا تسريب للمفاتيح في الاستجابات.                                                                                             |
| 1.15 | **عدم تسريب المفاتيح في السجلات**      | جيد     | `sanitizeForLog` يحذف حقول مثل password, token, secret, api_key, jwt_secret, supabase_service_key.                                                                       |

**ملخص الأمان:** جيد — JWT، cookies، RBAC، rate limiting، validation، MFA، وعدم تخزين/تسريب مفاتيح مناسبان للإنتاج. تشغيل migration 011 يفعّل logout-all و MFA بالكامل.

## 2. تحليل الأداء

| #    | البند                             | التقييم | الملاحظات                                                                                                                         |
| ---- | --------------------------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 2.1  | **قياس latency لكل endpoint**     | متوسط   | وجود `/metrics` مع histogram للمدة؛ لا يوجد قياس منفصل لكل endpoint رئيسي (p50/p95/p99) في التقرير؛ يمكن استخراجها من Prometheus. |
| 2.2  | **مهلة الطلب (Request timeout)**  | جيد     | مهلة عامة (مثلاً 15 ثانية) عبر middleware؛ قابلة للتكوين بـ `REQUEST_TIMEOUT_MS`؛ استجابة 503 عند انتهاء المهلة.                  |
| 2.3  | **استخدام CPU/RAM**               | متوسط   | عملية Node واحدة؛ لا قياس مدمج لاستخدام الموارد؛ الاعتماد على مراقبة المنصة (مثل Render).                                         |
| 2.4  | **اتصالات DB**                    | جيد     | استخدام Supabase (اتصال مُدار)؛ لا إنشاء اتصالات خام غير مضبوطة في الكود.                                                         |
| 2.5  | **حجم الاستجابات (Payload size)** | متوسط   | حد هيئة الطلب 15mb؛ لا حد صريح لحجم الاستجابة؛ قوائم كبيرة (مثلاً منتجات بدون pagination كافٍ من الواجهة) قد تزيد الحجم.          |
| 2.6  | **Pagination في القوائم**         | جيد     | `parsePagination` موحّد؛ حدود (مثلاً 500 افتراضي، 1000 أقصى) لـ products، orders، notifications، admin؛ استعلامات محدودة.         |
| 2.7  | **استخدام الكاش (منتجات)**        | جيد     | cache middleware لـ GET المنتجات (TTL 600s)؛ دعم Redis عند `REDIS_URL`؛ إبطال عند إنشاء/تحديث/حذف منتج.                           |
| 2.8  | **N+1 / استعلامات دفعة واحدة**    | جيد     | السلة تجلب المنتجات دفعة واحدة؛ خدمات المنتجات والإدارة تستخدم تجميع عند الحاجة.                                                  |
| 2.9  | **ضغط الاستجابة (Compression)**   | جيد     | استخدام `compression` middleware.                                                                                                 |
| 2.10 | **فهرس قاعدة البيانات**           | جيد     | وجود migrations لفهارس آمنة (مثلاً users، products، orders، order_items، carts، notifications).                                   |

**ملخص الأداء:** جيد في المهلات والـ pagination والكاش والاستعلامات؛ متوسط في قياس latency والموارد وحجم الاستجابات (يمكن تحسينه بفلترة/تقسيم من الخادم ومراقبة).

## 3. الصلاحية للتوسع

| #   | البند                    | التقييم     | الملاحظات                                                                                                                                         |
| --- | ------------------------ | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 3.1 | **>10k منتج لكل تاجر**   | جيد         | Pagination في API (limit/offset)؛ فهارس على `merchant_id` و `(is_active, status)`؛ الخادم يتحمل مع pagination.                                    |
| 3.2 | **واجهة كتالوج ضخم**     | متوسط       | كتالوج عام يعتمد على جلب قائمة منتجات ثم فلترة من الواجهة؛ مع عدد كبير جداً من المنتجات عالمياً قد يصبح بطيئاً؛ يُفضّل فلترة/بحث من الخادم.       |
| 3.3 | **>10k مستخدم متزامن**   | يحتاج تحسين | بنية بدون حالة (JWT فقط) مناسبة للتوسع؛ لكن تشغيل instance واحد سيكون عنق زجاجة؛ يحتاج عدة instances + موزع حمل + Redis للمشاركة (كاش/حد المعدل). |
| 3.4 | **نقاط اختناق**          | متوسط       | عملية واحدة؛ حد المعدل مخزّن في الذاكرة (مع عدة instances يحتاج Redis أو غيره)؛ استعلامات إدارية ثقيلة قد تحتاج حدود pagination إضافية.           |
| 3.5 | **استدعاءات N+1**        | جيد         | معالجة في السلة والمنتجات؛ لا أنماط N+1 واضحة متبقية في المسارات الرئيسية.                                                                        |
| 3.6 | **قابلية التوسع الأفقي** | جيد         | لا تخزين جلسة على الخادم؛ Redis للكاش (وعند الرغبة لحد المعدل) يدعم عدة instances.                                                                |

**ملخص التوسع:** جيد لدعم عدد كبير من المنتجات لكل تاجر مع pagination؛ دعم >10k مستخدم متزامن يحتاج تحسين تشغيلي (عدة instances، موزع حمل، Redis).

## 4. الصيانة والهيكلية

| #   | البند                                  | التقييم | الملاحظات                                                                                                        |
| --- | -------------------------------------- | ------- | ---------------------------------------------------------------------------------------------------------------- |
| 4.1 | **تقسيم واجهات/شاشات الفرونت**         | جيد     | CustomerView و MerchantView: تبويبات مكوّنة من مكونات فرعية مع `React.lazy` و `Suspense`؛ تحميل كسول للتبويبات.  |
| 4.2 | **شاشة الإدارة (AdminView)**           | متوسط   | مكوّن كبير؛ التبويبات غير مفككة إلى مكونات كسولة مثل Customer/Merchant؛ يُفضّل تقسيمها لاحقاً.                   |
| 4.3 | **إعادة استخدام خدمات/مكونات الفرونت** | جيد     | مكونات مشتركة (مثل CustomerShared، ConfirmModal)؛ خدمات (productService، cartApi، authService)؛ hooks (useCart). |
| 4.4 | **طبقة Validation مركزية**             | جيد     | Joi في `validation/schemas.js`؛ middleware `validate()`؛ تطبيق على المسارات الحرجة.                              |
| 4.5 | **هيكل الباكند**                       | جيد     | مسارات → controllers → services → DB؛ middlewares منفصلة (auth، أمان، تحقق، مهلة، سجلات، مقاييس).                |
| 4.6 | **تقسيم الخدمات**                      | متوسط   | بعض الخدمات كبيرة (مثل adminService)؛ يمكن فصلها حسب النطاق (مستخدمون، طلبات، منتجات، منصة) لاحقاً.              |
| 4.7 | **توحيد Pagination**                   | جيد     | `parsePagination` في `utils/pagination.js` مستخدم في الخدمات ذات القوائم.                                        |
| 4.8 | **السجلات والمقاييس**                  | جيد     | logger موحّد؛ requestId؛ مقاييس طلبات، أخطاء، مدة، حد معدل، تحقق، MFA في `/metrics`.                             |

**ملخص الصيانة:** هيكل واضح وطبقة تحقق مركزية وتقسيم جيد لشاشات العميل والتاجر؛ تحسين محتمل لـ AdminView وتقسيم بعض الخدمات الكبيرة.

## 5. التقييم الشامل

### نقاط القوة

| البند | الوصف                                                                                                                                                                   |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| أمان  | JWT مع httpOnly، RBAC واضح، حد معدل عام ومحدد للمنتجات والـ auth والدفع، تحقق Joi على المسارات الحرجة، MFA اختياري، إلغاء الجلسات (logout-all)، عدم تخزين/تسريب مفاتيح. |
| أداء  | Pagination موحّد، كاش للمنتجات (مع Redis)، ضغط، مهلة طلب، فهارس DB، تقليل N+1.                                                                                          |
| توسع  | بنية بدون حالة؛ دعم Redis للكاش؛ pagination يسمح بعدد كبير من المنتجات لكل تاجر.                                                                                        |
| صيانة | تقسيم واجهات العميل والتاجر، validation مركزية، هيكل باكند واضح، مقاييس وسجلات منظمة.                                                                                   |

### المخاطر الحالية

| المخاطرة                                             | المستوى | ملاحظة                                                   |
| ---------------------------------------------------- | ------- | -------------------------------------------------------- |
| تشغيل instance واحد فقط                              | متوسط   | تحت حمل عالٍ قد لا يكفي لـ >10k متزامن؛ يحتاج توسع أفقي. |
| كتالوج يعتمد على جلب كل المنتجات ثم فلترة من الواجهة | متوسط   | مع نمو كبير للمنتجات عالمياً قد يزيد زمن التحميل والحجم. |
| AdminView كبير بدون lazy tabs                        | منخفض   | يؤثر على حجم الحزمة وسهولة الصيانة فقط.                  |
| عدم تشغيل migration 011                              | منخفض   | logout-all و MFA لن يعملا حتى يُشغَّل الـ migration.     |

### توصيات سريعة (بدون كسر البرودكشن)

| الأولوية | الإجراء                                                                              | التأثير                    |
| -------- | ------------------------------------------------------------------------------------ | -------------------------- |
| 1        | تشغيل migration 011 على DB الإنتاج لتفعيل token_version و MFA.                       | تفعيل logout-all و MFA.    |
| 2        | مراقبة `/metrics` (مثلاً ربط Prometheus/Grafana) وضبط حدود المعدل من env عند الحاجة. | مراقبة وتحكم أفضل.         |
| 3        | عند النمو: تشغيل أكثر من instance + موزع حمل + Redis للكاش (وحد المعدل إن أردت).     | استعداد لـ >10k متزامن.    |
| 4        | لاحقاً: فلترة/بحث كتالوج من الخادم مع pagination بدل جلب كل المنتجات.                | أداء أفضل للكتالوج الكبير. |
| 5        | لاحقاً: تقسيم AdminView إلى تبويبات كسولة وتفكيك adminService حسب النطاق.            | صيانة وحزم أفضل.           |
